# 1. UDP 必要可靠性优化

## 1.1 目标与实现

本轮仅处理稳定运行所需的三项：压力下的回收能力、会话管理故障隔离、面板运行诊断。继续使用官方 sing-box，不引入 realm 或自编译内核。

固定转发的 UDP 通路新增独立六秒健康租约；只匹配客户端 UDP 入站和对应 UDP 回包，不关闭 TCP 或共享 WireGuard 隧道。租约由 root 会话工作线程续期，普通网络监测器无权续期。会话 API 或 conntrack 连续故障会撤销租约，即使撤销命令失败，内核也会自动使旧租约到期。恢复前仅清理固定转发 UDP 会话，再重新开放，代理进程无需重启。普通代理节点 UDP 不在这套回收与健康保护的范围。

回收每轮最多处理 512 个到期会话，最多八个并发关闭请求，避免大量到期会话拖住健康续期；超额待回收会话保留到后续轮次，不重置其空闲观察时间。单轮工作设四秒预算，大规模会话时降低快照频率至每轮完成后等待一秒。8192 会话流量下曾触发原一秒 API 超时，因此管理 API 请求期限调整为最长两秒。静态防火墙规则仍纳入既有完整性验证，修复后不会自行生成健康授权。

内核观察仅保留上一完整 API 快照中已见客户端的准入元组；新会话先建立空闲观察，再在后续轮次获得内核活动保护。已关闭出站 socket 的 conntrack 条目可能继续存在，不能占用客户端观察预算。启动验证仍读取完整有界内核快照，不把空白观察当成权限检查成功。

第二版 UDP 能力用于协商与本机持久化，旧 agent 无法取得新版启用配置，使用新版后不能降级到仅支持第一版回收的 agent。候选能力保留旧更新器认识的 `forward_udp: 1`，另以 `forward_udp_isolation: 1` 证明第二版能力，避免旧更新器因为基础字段版本不相等而拒绝升级。旧网络计划需要重新应用才能恢复 UDP，不能借用旧健康记录开放流量。

## 1.2 压测发现的容量问题

先以两条转发各配置 4096 会话运行真实流量，8192 个客户端虽能请求成功，实际只保留合计 2048 个会话，活跃映射发生替换。官方 [UDP NAT 实现](https://github.com/SagerNet/sing/blob/0ad23b637bd4/common/udpnat2/service.go) 的缓存容量固定为 1024；官方 direct 入站未提供扩大该缓存的配置选项。

因此启用时每条转发上限改为 1024，整机合计上限仍为 8192。预检、数据库变更、期望配置与最终编译重复核验。旧 4096 记录保留读取、停用与删除能力，超量启用会被阻断，须先减少配置。不会截断用户保存值后假装原配置已经成功应用。

## 1.3 运行诊断

面板显示健康、重试、暂停、准备中及未启用状态，并展示最近观测会话数、本次 agent 运行累计清理次数和检查耗时。错误原因只上报固定分类：会话 API、内核会话观察、健康保护规则或本机代理未就绪，不上传原始错误、来源地址或本机认证密钥。

离线、无诊断或诊断超过 45 秒时，显示等待确认，不沿用历史健康状态。计量仍使用原有独立账本，不把管理 API 计数叠加进流量。

## 1.4 验证状态

真实验收全部使用临时隔离容器，没有连接真实 VPS。ARM64 systemd 与 Alpine/OpenRC 的 UDP 暂停、恢复、计量和清理已执行；TCP+UDP 场景增加故障前建立的 TCP 长连接检查。压力测试使用八条转发、每条 1024 个客户端，持续流量后保留 64 个活跃客户端，验证其余容量回收并重新填满。

```sh
UDP_STRESS_SECONDS=600 NETWORK_SYSTEMD_CASE=forward-stress \
  NETWORK_TEST_ARCH=arm64 SINGBOX_BIN=/path/to/verified/official/sing-box \
  bash scripts/test-network-systemd-container.sh
```

WireGuard TCP+UDP 故障注入还验证了同一隧道中已建立的 TCP 连接仍能传输，UDP 恢复不重启核心进程。

原生 AMD64/ARM64 CI 均加入同一压力测试。本机 AMD64 仿真的 seccomp 限制仍存在，不能将交叉编译或工作流静态校验写成原生 AMD64 流量验收。

## 1.5 交付

本地候选为 `release/v0.1.999-issues.5`，第一版 `.4` 不包含这些优化。未 commit、push、签名、发布或进行真实 VPS 操作。

十分钟持续流量段完成两轮，8192 个会话的 UUID 全程保持稳定；原整轮收尾失败，不将这些整轮命令计为成功。收尾分别发现夹具等待心跳期间停止保活的误判，以及真实的出站 conntrack 残留误占客户端观察预算的问题。已修正夹具保活与准入观察范围，保留每轮 512 个回收限额。

最终独立完整生命周期复测通过：八条转发共 8192 个客户端，60 秒内 48 轮持续流量没有替换活跃映射；保留 64 个持续发包客户端，验证其 UUID 不变、清理计数恰好增加 8128；再填满 8192 并持续发包直到健康诊断匹配，未发生额外清理或进程重启。代理 RSS 起始约 222.0 MiB，峰值约 244.6 MiB，重新填满后约 231.7 MiB。CI 默认仍为 600 秒，将持续负载和严格收尾串联；本地最终结果按“两轮十分钟持续负载片段 + 修正后的 60 秒完整生命周期”记录。

Linux 专用回归构造达到整个客户端预算三倍的旧出站条目，验证其不消耗 8192 个客户端准入名额；真实 ARM64 Linux 解析及过滤测试通过。准入范围修正后的会话、agent、core race 与 TCP+UDP 故障隔离回归通过；最终 Alpine/OpenRC 512 MiB 的 UDP 持续流量、故障隔离、无重启恢复、端口编辑和退役结算也通过，未 OOM。

十分钟片段中的代理 RSS 采样约为 229–247 MiB；30 秒 CPU 样本中，代理平均约占用 5.86 个逻辑核，agent 约占用 0.14 核。这是 ARM64 隔离环境持续向全部 8192 个会话发包的强负载数据，不能把整机配置预算当成小内存或单核 VPS 的推荐并发。

完整项目检查通过；最后界面补充后，47 项前端测试、typecheck/build 与 Chrome 诊断状态、旧配置提示、移动布局、Cookie/CSRF/CSP 回归通过。会话回收、agent、网络保护与更新兼容的 race 检查通过；ShellCheck、actionlint、API 契约与 diff 空白检查通过。使用两版实际 ARM64 附件验证了旧更新器接受新版候选，以及新版状态拒绝降级。

本地交付核对项目包括双架构附件 SHA256、归档内控制端/agent/安装器/文档以及最终嵌入的界面资源。正式签名发布、公开下载与原生 AMD64 CI 尚未执行。

## 1.6 原生 AMD64 资源约束复核

v0.1.7 发布 CI 的原生 AMD64 runner 在 8192 个 UDP 会话下，官方 sing-box 1.14.1 RSS 达到约 473–493 MiB；`GOMEMLIMIT=192MiB` 已生效，匿名透明大页约占 160–188 MiB，文件大页约占 74 MiB，384 MiB RSS 门槛因此阻断发布。该宿主策略与此前 ARM64 本地数据不同，不能用历史结果替代本轮原生验收。

代理启动环境固定使用 `GODEBUG=disablethp=1`，只针对官方 sing-box 进程的 Go 堆，不继承任意宿主 `GODEBUG`，不改变全局内核策略或官方二进制。兼容依据见 [Go 官方运行时问题说明](https://go.dev/issue/64332) 与 [GC 指南](https://go.dev/doc/gc-guide#Linux_transparent_huge_pages)。服务单元同时记录该参数，以使已有单元在重新应用配置时更新；原有软硬预算保留。

验收容器显式启用 1 GiB 父级内存限制且不增加 swap，并要求代理叶 cgroup 实际 `memory.max=268435456`，持续检查 OOM kill。600 秒、8192 会话、活跃映射身份、8128 个闲置会话回收、重新填满及 384 MiB RSS 门槛均保留。本轮完整通过结果以修复提交的原生 CI 为准，不能仅凭参数已写入认定通过。

验收夹具从进程 cgroup 成员记录和 mountinfo 共同定位内存控制器，兼容 unified v2 与 hybrid/v1 内存挂载；不把 `0::` 的存在等同于 memory 控制器可用。正式流量前启动独立的 systemd 限额探针，核对实际内核 256 MiB 上限；环境不满足时立即失败并打印层级信息，不等待业务配置和十分钟负载。

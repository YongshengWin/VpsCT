# 升级稳定性与验收

[返回 README](../README.md) · [安装、升级与恢复](operations.md) · [维护者发布流程](releasing.md)

网页升级涉及控制端、agent、内核和节点配置四个阶段。程序更新完成、配置已应用、客户端可连接分别确认，避免把其中一个阶段的成功当作整条链路恢复。本说明记录当前实现与验收边界，不表示所有历史版本都具有相同保护。

## 1. 固定升级目标

### 1.1 发行版本与文件校验

控制端创建 agent 更新任务时，保存自身发行版本和对应架构文件的 SHA256。版本显示中的提交信息会去掉，例如 `v0.1.6 (abcdef1)` 使用官方 `v0.1.6` 校验清单；开发构建或缺少有效发行版本时不自动发起升级。新版 agent 自更新和独立维护 worker 都用任务中的确切版本验证，不在执行时改用上游 `latest`。

下载地址带目标 SHA256。控制端只打开一次分发文件，从同一个文件句柄校验并发送内容；已切换为另一版本时拒绝该下载，避免把新内容交给旧任务。agent 仍检查长度、文件 SHA256 及所配置的发行验证策略。默认策略使用官方 HTTPS 来源与 SHA256，文件完整性校验不等于发布者签名验证；显式启用的安全更新策略继续生效。

### 1.2 离线与过时任务

服务器离线期间控制端再次升级，尚未领取且目标已变化的 agent 更新任务会取消，旧任务不再可领取，再按当前目标排队。领取接口也检查目标，延迟送达的旧命令不能开始安装已被替代的文件。已经领取的 worker 先结束，新的目标不会与它并行替换程序。

agent 任务超过 15 分钟未领取会过期；过期及未执行的取消不消耗下载重试次数，不会永久阻断上线后的更新。旧卸载任务过期后不会重放。旧版 agent 的协议兼容路径仍保留，但新 agent 无法从旧控制端取得有效发行版本时会安全拒绝更新，应先升级控制端。

## 2. 有限重试与结果对账

### 2.1 自动重试边界

支持维护协议的自动同步使用与网页手动升级相同的持久化任务及回退执行器。只有在替换程序前、被执行器明确归类为临时下载失败的情况才自动重试；同一目标 SHA256 最多累计三次执行，第一次失败后至少等待 1 分钟，第二次失败后至少等待 5 分钟，之后由心跳触发重试。

文件超限、SHA256 不符、发行信任失败、兼容性失败、已经回退、回退失败及执行结果待核实不自动重试。任务历史查询不受面板展示条数限制，较早的安全失败不会因翻出最近记录而被遗忘。需要重试时，管理员在网页重新认证后创建明确的新任务。

网络恢复后 agent 必须重新上线，才能领取任务或触发下一次同步。有限重试不能修复 DNS、TLS、出站防火墙、GitHub 不可达或供应商网络故障；这些情况需按 worker 日志与实际网络检查处理。

### 2.2 程序完成与节点恢复

维护 worker 安装程序后，检查 systemd 主进程实际运行文件的 SHA256，并观察其稳定运行；失败时按验证过的恢复点尝试回退。worker 完成程序检查后释放维护及配置锁，agent 才继续应用节点配置。worker 不在锁内等待节点收敛，避免阻塞执行配置所需的同一把锁。

最终结果写入 root 保存的任务记录，再用当前任务的临时凭据回传。回执丢失时不会立即凭新文件心跳宣告成功，因为仍运行的 worker 后续可能回退。超过一小时执行时限后，仅当任务记录了不同的旧 SHA256、恢复后的心跳报告任务目标且任务为结果待核实，控制端才补记「心跳确认」。同 SHA256 重装、缺少旧文件记录、明确失败或回退均保留原结果。

「程序更新完成」和「心跳确认」均不证明代理流量可用。随后检查目标 agent 版本、节点应用回执、内核运行状态，再使用客户端测试连接。

## 3. 订阅与旧服务连续性

### 3.1 逐节点应用回执

控制端在发布配置时保存节点的候选快照。只有对应服务器、配置 revision 与 hash 匹配的成功回执，才将该节点标记为已应用；新版 agent 可逐节点报告结果，一个内核失败不覆盖其他内核已经成功的节点。旧 agent 的整份配置成功回执仍受同样的发布记录校验，失败回执不会推进全局已应用版本。

受管订阅从确认的节点快照生成，同时检查当前节点、服务器及分享授权。新增节点、修改密码、端口或网络配置等尚未确认应用时，不提前向客户端分发这些参数。已确认且当前配置与授权仍匹配的节点，不因 agent 暂时离线而删除；升级时可利用原数据库中精确匹配的历史成功回执补齐确认记录，不能凭在线状态或节点存在推断成功。外部导入节点不需要 agent 应用回执。

停用、删除、撤销、分享暂停或到期、配额耗尽、出口停用等当前限制优先于旧快照。旧回执和迟到回执不能重新开放已禁止的资源。门禁可阻止未应用参数进入订阅，但不代替公网连通性测试，也不能保证客户端主动刷新订阅。

历史版本尚未保存独立客户端投影，补齐确认记录只能结合精确的历史配置回执和当前数据库上下文重建；无法证明一致时等待重新应用。新发布的配置保存完整加密投影，客户端参数变化也会生成新 revision。链式节点保存来源节点身份；旧数据只在解密参数与唯一来源完全匹配时补齐，来源不明或有歧义时不发布，来源删除后不会绑定到后来出现的同地址节点。

### 3.2 保留安全有效的旧服务

下载选定内核暂时失败时，agent 可以保留仍在运行的旧服务，条件是现有进程身份、节点及网络运行配置与当前授权一致。此检查包含节点、端口、协议参数及解析后的网络配置；密码轮换、私网或传输授权撤销、停用资源等变化后，不会将旧服务当成可继续使用的服务。保留旧服务不会伪装成目标内核版本安装成功，页面仍需显示等待或错误。

内核安装与激活分别记录恢复阶段，备份旧二进制、可信记录、配置、systemd 服务状态及文件指纹。恢复前验证备份所有者、路径范围和 SHA256；未完成的激活在下一次应用前恢复。旧服务是否可以重启，还要比对当前凭据、资源限制及本地授权的安全指纹；指纹变化时不自动重启旧服务。

恢复范围不包含旧 nftables 授权、计量状态或 root 安全策略。密码、配额或本机授权已被撤销时，不能通过回退内核恢复访问。这些保护针对程序与配置切换故障，不修复外部网络中断。

历史内核首次迁入时可能没有本机安全与运行指纹，此时不能证明旧服务可安全保留，需要先完成一次成功应用。保护检查失败后，即使恢复了旧文件，也会停止相关内核；恢复本身失败同样停止服务，避免回退重新开放已被拒绝的访问。

## 4. 数据库与控制端恢复

### 4.1 控制端就绪检查

普通 `/healthz` 保持进程存活检查。安装器启动和回退后使用仅限本机直连的 `/healthz?ready=1`，检查数据库访问、节点及订阅等加密数据读取、服务器配置构建和AMD64 agent 分发文件。反向代理请求不能触发该检查；检查不访问上游、外部订阅或 VPS，也不代表公网连接已恢复。

### 4.2 程序与快照配套恢复

启动时先读取数据库 schema 版本，当前程序遇到比自身迁移范围更新的库时拒绝继续迁移及提供服务，并要求恢复配套的升级前备份。因此控制端回退必须同时恢复旧程序、环境与停服数据快照，不能只把二进制换回旧版。已经发布且未包含该检查的历史程序并不会自动获得保护，操作要求同样适用。

安装器自动恢复先认证解密加密快照，并在暂存目录完整解包，确认成功后才移动当前数据并替换。失败现场和旧备份保留；自动恢复成功仍以退出码 `20` 标记本次升级失败。自定义数据目录、挂载布局及手动或 Docker 部署按各自备份恢复流程处理，具体命令见 [更新失败后的恢复](operations.md#6-更新失败后的恢复)。

## 5. 验收与发布门禁

### 5.1 回归测试

| 层次 | 验证内容 | 入口 |
|---|---|---|
| 任务与版本 | 确切发行验证、下载错误分类、三次上限与退避、过期重排、过时队列拒绝、完整失败历史、丢失回执对账及同文件重装不伪成功 | `internal/maintenance`、`internal/api`、`internal/agent` 专用测试 |
| 节点与恢复 | 已发布配置回执校验、逐节点订阅门禁、当前撤销优先、内核恢复指纹及新版 schema 拒绝 | `internal/store`、`internal/core`、`internal/subscription` 专用测试 |
| 网页维护 | 真实 systemd、独立 worker、升级及卸载执行与失败路径 | `scripts/test-maintenance-container.sh` |
| 真实历史升级 | 官方 `v0.1.5` 到最终候选附件，原订阅流量、离线旧 agent、自动同步及固定版本重装 | `scripts/test-web-upgrade-container.sh` |

真实历史测试先用 `scripts/fetch-upgrade-fixture.sh` 获取并核对官方旧版附件，不能把新源码改成旧版号充当历史版本。容器禁止外网，只替代 GitHub 发行下载传输；实际控制端、agent、systemd、默认 SHA256 策略和官方 sing-box 1.14.1 客户端均参与执行。通过网页维护 API 升级后，使用升级前的同一份订阅代理域名 HTTP/HTTPS 请求，并检查目标进程报告、内核运行及应用状态。运行方法见 [安装、升级与恢复验收](releasing.md#23-安装升级与恢复验收)。

### 5.2 验收范围与附件发布

历史网页测试当前覆盖宿主架构的 Shadowsocks 路径，不能据此宣称全协议、UDP、中转、多网卡、所有 Linux 发行版或公网安全组均已验证。测试使用旧附件内的安装器启动历史升级，新版安装器的回退实现仍需独立故障测试。跨架构构建成功不等于该架构的实际运行验收。

Release 工作流先运行 CI，再打包候选附件；草稿创建依赖这些最终附件通过历史网页升级测试。工作流还核对官方旧附件和官方 sing-box 资产 SHA256，任何下载、校验或测试失败都阻止创建草稿。当前自动附件门禁运行于 Ubuntu 24.04 AMD64；其他运行范围记录于 [验收记录](readiness.md)。

本地发布也必须对最终上传的附件运行同样门禁，并保留提交、版本、架构、SHA256 清单和结果。验收后重新构建或修改附件时重新验收，不把源码检查结果或前一份附件日志直接用于新文件。创建草稿、推送及公开发行仍需维护者明确授权。

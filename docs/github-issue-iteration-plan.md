## 2. 第一阶段：恢复节点部署与配置收敛

### 2.1 #32：能力检查不能靠统一加权限修复

首先复现“普通节点 / 绑定出口节点 × 公共 / 私网权限组 × systemd / LXC”，记录宿主内核、实际 capability、SO_MARK 结果、最终服务定义和真实 cgroup。LXC 使用宿主内核，不能从发行版名称推断能力。

Linux 手册明确：SO_MARK 需要 CAP_NET_ADMIN，或在 Linux 5.17 起使用 CAP_NET_RAW。因此“缺少 NET_ADMIN 必然失败”不能直接作为通用结论。当前启动器每次运行 sing-box 都探测 SO_MARK，而权限生成由 `marked` 控制，需要核实每条调用路径是否一致。依据见 [socket(7)](https://man7.org/linux/man-pages/man7/socket.7.html)。

实施选择：

1. 将配置实际需要的 mark 能力、预检要求和运行态允许权限统一为同一策略，避免未使用 mark 的配置被无条件探测阻断。
2. 对需要 mark 的路径，以最小权限执行实际探测；不支持时在替换现有服务前返回明确的环境不兼容错误。若要支持必须 NET_ADMIN 的旧内核，单独评估网络隔离边界，不在此次修复中默认扩大全部代理权限。
3. 检查最终 unit 和 drop-in 的 Slice 来源，尽量只产生一个有效目标。issue 对多 Slice 的解释暂列假设，需用真实 systemd 复现，不能只凭文本重复断定行为。
4. 如增加 cgroup 校验，按受管 Slice 的规范化路径和完整层级边界匹配，并验证 MainPID 实际归属；不能使用包含字符串或任意父 Slice 作为成功条件。Slice 与运行进程归属冲突时明确失败。
5. 独立检查日志目录及文件的最小权限、专用账号写入和服务启动诊断；不把父目录整体改为代理可写。

主要边界：`internal/core/isolation.go`、`internal/core/systemd.go`、`internal/proxysandbox/filter_linux.go`，并回归 OpenRC 对等的权限策略。

验收：普通与绑定出口节点均能在支持环境启动，真实客户端完成 DNS、HTTP/HTTPS 及对应 TCP/UDP；旧内核或受限容器在预检阶段给出可行动提示；错误账号、错误 cgroup、额外 capability 仍被拒绝。反馈的运行环境必须进入复现矩阵。

### 2.2 #33：证明规则不影响监听目的端口

保留现有严格兼容路径，新增受限的 nft JSON 分析，不根据表名或 fail2ban 名称直接放行。

1. 新路径先要求外来 input 基链 `policy=accept`，再逐条证明规则不会匹配任一受管 TCP/UDP 监听端口；policy drop/reject 不能因为规则端口不重叠而通过。
2. 第一版支持明确的 TCP/UDP `dport` 等值、内联集合和闭区间，校验协议、操作符、端口边界以及规则组合。无法解析的命名集合、否定比较、拼接映射、动态内容或未知表达式保守拒绝；xt multiport 继续走已有只读交叉核对。
3. `sport` 是远端客户端源端口，不能和本地监听端口作不相交比较。只有 sport 的规则不能证明安全。规则即便包含 dport，也须排除未知表达式在匹配前改变数据或产生副作用。
4. accept/drop/reject/jump 等动作只在受支持的表达式顺序中判断；无法证明副作用仅发生于匹配成功路径时拒绝。无端口限制规则不走快速路径。空 permissive 链维持当前行为，空 default-drop 链拒绝。
5. 只修改 VpsCT 自己带标记的规则。规则重载、节点改端口、停用、删除及转发资源均重新验证；不改写外部防火墙，不以独立 accept 链绕过其他 drop 链。

主要边界：`internal/nft/ingress.go`、`internal/nft/ingress_compat.go` 及对应单元/内核测试。

验收矩阵必须包含：原生 nft fail2ban、iptables 直接 dport 规则、原有 multiport、IPv4/IPv6、TCP/UDP 同号端口、集合/范围边界、端口重叠、sport-only、default-drop、无端口规则、未知表达式及防火墙重载。用真实 nftables 验证 SSH 防护和其他服务规则保持有效，并确认节点端到端可用。

### 2.3 两个故障共用的状态与重试

将失败分为内核能力、服务启动、cgroup 归属、主机入站规则和公网连通性，保留阶段、稳定错误码及脱敏摘要。agent 在线、进程 active、配置已应用和公网可达分别表达。

确定性错误按“配置修订 + 错误类别”聚合提示并限制重复日志；网络瞬态错误退避重试。防火墙快照或环境能力改变后允许重新检查，不能因停止刷日志而永远不恢复。禁止在尚未完成入站或隔离检查时谎报 applied。

先在 API 和 agent 结果中承载诊断，再以现有服务器/节点状态组件显示原因。可见行为变更须浏览器检查明暗主题与窄屏。

## 3. 第二阶段：Alpine 与网络能力收尾

### 3.1 #26：按能力明确支持范围

当前 AGENTS.md 仍记载 Alpine 首版仅支持 sing-box、无网页维护，而 README 与新增源码已描述 mieru 和网页维护。实施前对照最终发行目标统一说明；不是直接把较新的文档当成已发布事实。

| 能力 | 当前证据 | 下一步交付 |
|---|---|---|
| Alpine agent 自动识别与安装 | `install-agent.sh`、`internal/openrc` 已实现 | Alpine 3.23 双架构首次注册、终端更新、重启自启验收 |
| 官方 musl sing-box | 历史 ARM64 容器记录 | 双架构安装与实际 TCP/UDP，明确 cgroup v2/隔离前置条件 |
| 官方 mieru | 2026-10-14 ARM64 BPF 计量记录 | AMD64 运行、bpffs/BPF 缺失失败、重启续计与退役结算 |
| agent 网页维护 | 有 ARM64 测试替身验收 | 正式候选附件校验、成功升级、失败回滚及任务恢复 |

历史证据见 [Alpine 扩展记录](alpine-mieru-maintenance.md)。其中维护使用本地候选和校验替身，不能代替官方发行下载验收。使用 `scripts/test-alpine-container.sh`，小内存优先验证 256/512 MiB；128 MiB 保持实验标记。

关闭条件：承诺的最小范围进入正式 Release，双架构运行证据、安装与迁移步骤可复用，限制写清楚。更大的 mieru/维护范围可分后续批次，不能阻塞已验收的基础支持，也不能提前宣传。

### 3.2 #17：把组合能力变成可用流程

按 [网络指南](network.md) 已有资源模型实施，不增加第二套“专线节点”系统。

1. 明确区分监听网卡、出口网卡、计费网卡和订阅访问地址；用一个完整示例演示创建、预览、应用回执及客户端验证。
2. 将 SSH/WireGuard 出口与客户端入口协议分别列示。SSH 保持主机公钥固定与仅 TCP；WireGuard 明确是业务出口，不承诺整机 VPN。
3. 最小发布矩阵为 sing-box 节点分别经 direct、SSH、WireGuard，以及 mieru 当前支持的监听/出站方式。验证真实出口、DNS、网卡消失后的阻断和重启恢复；不宣称所有入口与出口任意组合。
4. 网卡改名、删除重建、地址变动、配置预览过期、配额阻断与计费接口切换进入回归。不得把接口流量与节点流量要求相等。
5. 单独列出未支持的 Snell/mieru 隧道出口、整机 VPN、任意多跳、故障切换和带宽叠加；先核实需求再排期。UDP 固定转发继续受官方内核验证限制。

关闭条件：已答复的基础能力具有明确版本和可复现使用路径；尚未支持的请求拆成独立范围。issue 状态调整及回复在实施交付后按用户授权执行，本次仅提出建议。

### 3.3 #16：保留反向代理回归

覆盖保留 Host、可信代理单值 X-Forwarded-Host、非可信伪造头、错误域名、多值头和 SSE。脚本安装与 Docker 使用同一站点约束；不关闭 Host 校验解决配置问题。沿用 [运维配置与排查](operations.md) 的反向代理示例。

## 5. 发布门槛与回滚

1. 实施前固定源码及现有工作区改动清单，不丢弃用户改动，不把未经验证的其他功能混入修复包。
2. 按变更完成针对性测试及 `make check`；前端修改执行 typecheck/build 和浏览器验收；Linux amd64/arm64 均构建，关键网络行为均实际运行。macOS 单元测试与交叉编译不能代替 Linux 运行证据。
3. 复用现有 systemd/nft、Alpine 和维护隔离容器；补充宿主内核能力受限的 LXC 场景。容器不能模拟所有旧内核差异，缺少环境时明确列为未验收。
4. 候选制品执行旧版升级、配置重生成、任务恢复及失败回滚。记录官方内核版本、架构、系统、校验方式、候选程序摘要和实际结果。只信任受支持的官方内核。
5. 代理越权、错误 cgroup 被接受、改写外部防火墙、错误报告 applied、身份/配置丢失或回滚失败均阻断发布。
6. 第一批优先保持无 schema 迁移；如状态持久化必须新增字段，单独验证兼容迁移与回滚读取能力。不能静默恢复整库覆盖升级后的写入。
7. 通过隔离验收后，由用户指定目标和范围再安排单台试运行。GitHub 回复、关闭 issue、commit/push、Release 与远程部署均不在本次设计动作内。

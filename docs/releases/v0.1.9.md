## 1. 六种新增的受管组合

本版面向 **Linux AMD64**。在「服务器 → 部署节点」选择协议和传输方式。原有节点和省略组合的部署请求沿用旧默认值：VLESS 使用官方 sing-box 的 TCP + REALITY + Vision，Trojan 使用原生 TCP + TLS。升级无需重建这些节点。

| 新增组合 | 受管内核 | 部署时填写或核对 |
| --- | --- | --- |
| VLESS + XHTTP + REALITY | 官方 Xray 25.12.8 | REALITY 握手域名、XHTTP 路径（默认 `/`）、可选 Host 和模式。支持 `auto`（默认）、`packet-up`、`stream-up`、`stream-one`，不使用 Vision。 |
| VLESS + TCP + TLS | 官方 sing-box | 普通 TLS 证书域名（SNI）和证书模式，不使用 Vision。 |
| VLESS + WebSocket + TLS | 官方 sing-box | 证书域名、WS 路径和可选 HTTP Host。 |
| VLESS + gRPC + TLS | 官方 sing-box | 证书域名和必填的 gRPC 服务名。 |
| Trojan + WebSocket + TLS | 官方 sing-box | 证书域名、WS 路径和可选 HTTP Host。 |
| Trojan + gRPC + TLS | 官方 sing-box | 证书域名和必填的 gRPC 服务名。 |

六种组合均使用普通接入、默认监听和默认出口，要求本机安全策略与 nftables 计量可用。XHTTP 还要求 systemd、标准（`stable`）模式、独立公网入口且无 NAT 配置。精简模式和 Alpine/OpenRC 无法部署受管 Xray。

五种普通 TLS 组合可继承服务器证书模式，也可选自签、ACME 或 VPS 上已登记的外部证书。自签模式导出时沿用跳过证书校验的设置。WS 的 HTTP Host 可以与 TLS SNI 不同；sing-box 入站核对路径，如需按 Host 分流，应由前置 HTTP 服务处理。gRPC 客户端与服务端须使用相同的服务名。

## 2. 订阅格式与客户端选择

表中“可导出”表示 VpsCT 能在该格式中保留组合所需的握手参数。明文 URI 和 Base64 均需由具备对应协议能力的客户端导入。过滤入口时，订阅同时剔除依赖该入口的代理链并整理代理组；如果没有可用路径，预览或下载会报告不可用。

| 订阅格式或兼容档 | VLESS XHTTP + REALITY | VLESS 普通 TLS（TCP / WS / gRPC） | Trojan 普通 TLS（WS / gRPC） |
| --- | --- | --- | --- |
| 明文 URI、Base64 URI | 可导出，保留 path、Host、mode 与 REALITY 参数 | 三种均可导出 | 两种均可导出 |
| Mihomo | 可导出，需支持 XHTTP 的客户端内核 | 三种均可导出 | 两种均可导出 |
| 官方 sing-box 配置 | 过滤 | 三种均可导出 | 两种均可导出 |
| Surge 默认兼容档 | 过滤 | 全部过滤 | WS 可导出，gRPC 过滤 |
| Surge iOS 6.1+ / Mac 6.13+ 完整托管配置（显式选 `surge-vless`） | 可导出 | 三种均可导出 | WS 可导出，gRPC 过滤 |
| Shadowrocket 原生配置 | 过滤 | TCP、WS 可导出，gRPC 过滤 | WS 可导出，gRPC 过滤 |

## 3. Agent 能力、回执与分享

1. 部署前查询 `GET /api/v1/servers/{id}`。最近两分钟的心跳须报告 `xray_version=1` 或 `tls_transport_version=1`，对应的 `xhttp_block_reason` 或 `tls_transport_block_reason` 字段须存在且为空。旧 agent 可继续服务原有组合；部署新组合前先更新 agent，等待下一次能力上报。
2. 收到创建响应后，按 `Location` 查询节点，用 `X-Revision` 对照服务器的目标修订和配置哈希。新节点只有收到匹配 revision/hash 的 `applied` 节点回执才进入订阅。XHTTP 的回执须含 `core=xray` 和 `core_version=25.12.8`，普通 TLS 须含 `core=singbox` 和 `tls_transport_version=1`。收到 `202` 或超时时先核对已有节点及发布状态，避免重复创建。交付订阅前，用对应客户端通过代理取回预期正文。
3. 分享可为同一服务器的不同组合分配稳定入口 ID、独立端口和额度，并保留组合与证书选项快照。重新签发会轮换凭据并保留入口和累计用量。撤销后应等待 agent 应用清理，再确认缓存的旧凭据也无法连接。启用新组合后，服务器会持久记录所需 agent 能力；删除最后一个入口后仍保留此要求，以便完成清理。

## 4. 从 v0.1.8 升级与恢复

1. **先备份。** 停止写入，保存同一时点的旧控制端程序、完整数据目录（含 SQLite 数据库及 WAL）、加密密钥、环境文件、服务与 HTTPS 配置。Docker 部署配套保存旧镜像及 `/data`、`/keys` 卷快照。记录一份已有用量的旧分享，供升级后核对。备份步骤见[运维说明](../operations.md#43-备份数据)。
2. **按原部署方式升级控制端。** 原生安装使用目标版本安装器的 `--update --auto-rollback` 或网页维护；Docker 使用对应源码中的 `compose-upgrade.sh upgrade`。数据库自动从 schema 51 迁移至 54：52 引入独立分享入口并保留旧式分享，53 和 54 分别持久记录 Xray 和普通 TLS 的 agent 能力要求。确认控制端就绪、管理员可登录，再用原订阅检查旧分享的节点、端口、凭据、账期用量及额度状态。
3. **更新受管 agent。** 等待心跳、能力和节点回执后，再部署所需的新组合。控制端升级保留原有 sing-box 版本选择；五种普通 TLS 组合的双机实测版本为官方 1.14.1。XHTTP 按固定版本和摘要取得官方 Xray。
4. **需要回退时**，若已部署新组合，先用兼容 agent 撤销这些入口并核对清理回执。停止新版控制端，用升级前同一快照恢复旧程序、数据库、密钥和配置；Docker 恢复对应镜像与两份卷。避免让 v0.1.8 打开 schema 54 的库。恢复后核对 agent 心跳、原分享的额度与凭据状态，再用原订阅验证实际流量。快照之后的写入和撤销需逐项核对。[原生恢复](../operations.md#61-恢复安装器部署) · [Docker 恢复](../operations.md#62-恢复手动或-docker-部署)

# VpsCT 用户反馈迭代方案

本文为尚未实施的反馈方案，不自动纳入已完成功能。与其他工作重叠的改动须按代码逐项复核；未来版本当前已实现范围见 [v0.1.5 待发布说明](releases/v0.1.5.md)。

## 1. 目标与范围

本方案针对 agent 更新失败、服务器注册 401、节点批量导入成功后报错、在线状态不醒目四项反馈，并规划后续分享授权与连接日志体验。方案基于 2026-09-20 的代码检查和本地复现，尚未执行本方案中的修复、迁移或发布。

首要目标是让用户完成“添加服务器 → 安装 agent → 部署节点 → 导入或生成订阅 → 分享使用”的完整流程。保留轻量个人节点管理定位，复用已有分享、配额、到期与撤销能力；商业支付、订单、自动售卖不纳入本轮。

### 1.1 已确认事实与待验证项

| 反馈 | 已确认 | 尚需核实 |
|---|---|---|
| agent 官方发行校验失败 | 下载与控制端 SHA256 校验之后，还会独立校验发行来源；现有维护执行器未传目标版本，默认使用 latest；Docker 默认自行构建 dev agent | 反馈现场的发行来源、目标文件摘要、验证器能力和脱敏错误类别 |
| 升级显示 dev | 维护目标版本取控制端版本，未独立描述 agent 文件版本 | 反馈者是否使用默认 Docker 构建 |
| 多服务器注册 401 | 各服务器独立保存一次性令牌；本地测试不同服务器令牌均可成功注册；已用或被重新生成替代的令牌被拒绝；客户端统一吞掉 401 细分原因 | 是否复用了命令、令牌过期、注册响应丢失或第三方入口返回 401 |
| 导入成功后读取 null.length | 已通过实际 API 本地复现：成功解析与导入均可返回 errors:null；前端读取 errors.length 后中断成功回调 | 其他列表接口是否存在相同契约问题 |
| 在线不醒目 | 当前代码已有浅绿底徽章与明暗主题样式 | 反馈者的版本、主题及实际页面视觉效果 |
| 不能继续部署节点 | 升级校验失败发生在替换程序之前，不能据此认定旧 agent 不可用 | agent 在线、维护终态上报、配置收敛与内核安装的具体失败阶段 |

### 1.2 实施约束

- 本轮不绕过官方校验，不把控制端传入的摘要或清单当作独立发行信任来源。
- 不改变入站加出站的流量口径，不自动开启连接日志或在线 GeoIP。
- 维护验证使用隔离容器；真实机器仅在指定目标、明确授权范围内试运行，不执行卸载或清空验收。
- 工作区另有网络绑定、计费等进行中的改动。实施前固定基线，按路径隔离本方案改动，不把其他任务的改动一起提交或发布。
- 已有 Host 修复独立回归，避免此次更新影响已验证的反向代理兼容。

## 2. 交付阶段与顺序

| 阶段 | 优先级 | 交付物 | 完成标准 |
|---|---|---|---|
| A：恢复主要流程 | P0 | 导入契约修复；更新目标校验与禁用原因；结构化升级错误 | 不再出现成功导入却报错；不可验证的 agent 不会被自动派发 |
| B：统一发行与升级 | P0 | 独立 agent 元数据、精确版本校验、Docker 正式分发、旧版迁移路径 | 两种安装方式、双架构完成更新与失败恢复测试 |
| C：注册与批量安装 | P1 | 注册错误分类；令牌有效期与失效提示；批量逐台命令 | 不同服务器可独立并行安装，失败可定位到具体记录 |
| D：状态体验与完整验收 | P1 | 状态徽章、维护与在线状态分离、故障定位信息 | 明暗主题可辨识；完整业务流程通过 |
| E：分享授权完善 | P2 | 现有分享能力梳理、权限和日志范围说明 | 分享停用、恢复、到期、配额、撤销具有一致行为 |

开发先做导入小修复和 agent 发布链路，注册体验与视觉改进随后进入同一候选版本。阶段 E 单独评估、单独交付，不扩大故障修复版本范围。正式版本号在发布前确认，不覆盖已有 Release 附件。

## 3. Agent 发行与升级设计

### 3.1 分离版本与目标身份

控制端版本、当前 agent 版本、目标 agent 版本分别展示。目标身份包含：发行版本、组件、操作系统、架构、文件长度、SHA256、来源类型、升级协议能力。来源类型至少区分正式发行、开发构建和缺少元数据。

构建阶段生成每个架构的 agent 元数据文件，并随控制端安装包、Docker 镜像及发行附件一起分发。元数据与对应文件必须一致；不运行待验证的二进制来获取版本。控制端的普通页面和维护任务均使用同一目标解析入口，不能各自拼接版本。

元数据用于选择和描述文件，不赋予文件可信性。执行端仍必须从本机允许的官方渠道取得对应版本的校验资料并验证；网页不得传任意仓库、路径、命令或下载地址。

### 3.2 正式发行与 Docker

- 一次发行仅产生一套双架构 agent 文件，安装器与 Docker 分发相同字节。
- Docker 正式构建必须指定发行版本，取得并核验该版本官方 agent 附件；不得自行编译后宣称等同于官方附件。
- 源码开发模式可以构建 dev 控制端和 agent，但明确显示“开发构建，不能通过官方自动升级”，默认不自动下发此类文件。
- 发布流水线核对归档、镜像与附件中的 agent 摘要，发现不一致则阻断发布。
- 官方 SHA256 校验基于官方 HTTPS 来源，不把它描述成签名验证；显式启用 TUF 的部署继续遵循其原有策略。

### 3.3 精确版本与任务固定

任务创建时固定版本、架构和摘要；执行时下载与固定目标一致的文件，再按同一版本独立验证。校验接口显式接收 agent 的发行版本，禁止因为版本缺失静默回退 latest。

保留任务引用的文件直到任务结束；控制端切换发行版本不得改变已排队任务下载到的内容。采用固定格式、只读映射的目标标识，不允许客户端提供文件系统路径。过渡阶段若尚不支持保留多版本文件，目标变化必须让旧任务明确过期，而非继续下载不匹配文件。

创建任务前验证目标是否存在、架构是否匹配、元数据是否完整以及执行端是否具备所需能力。控制端预检通过并不取代执行端验证。

### 3.4 旧 agent 迁移

新增显式的精确版本升级能力字段，未报告时按旧协议处理；不能假设旧端会理解新增版本字段。控制端对不具备能力的端点显示迁移说明，不重复下发它必然无法验证的任务。

旧验证器只能使用 latest 时，先确认当前官方 latest 附件与目标完全一致，才允许沿旧链路更新；不能满足时，提供固定正式版本的可信终端更新流程。绝不通过改版本字符串、伪造摘要或关闭校验迁移。

终端流程在隔离环境验证：保留现有身份、状态、配置和回滚程序，完成更新后重新上报能力；明确禁止将“更新已注册 agent”误操作成重新注册。控制端先兼容新旧协议，再迁移单台 agent，最后按明确选择的批次开放。

### 3.5 错误与重试

维护结果添加稳定错误码、阶段和是否可重试，至少区分：目标不可用、元数据不完整、不支持的开发构建、发行目录无法访问、官方文件摘要不匹配、信任策略异常、空间不足、启动失败和回滚失败。

页面展示脱敏原因与针对性操作；保留错误摘要和必要审计信息，不回显 token、完整订阅路径或凭据。第三方响应体不得直接展示给用户。

同一服务器同一时刻仅执行一个维护任务。网络超时等瞬态错误允许有上限的退避重试；摘要不匹配和无效发行元数据不自动重试。失败目标保留记录，修正分发文件后可以产生新目标任务；对同一目标的人工重试保留现有二次认证要求。

### 3.6 升级状态不代替服务状态

分别展示 agent 在线状态、维护状态和节点配置应用状态。更新失败且旧程序仍运行时明确提示“原 agent 保留”，避免将整台服务器标成不可用。

验证维护失败终态能够上报、释放维护锁，并在后续心跳恢复正常配置收敛。升级失败后节点仍不能部署时，按配置下发、内核下载、配置校验、端口监听逐层定位。

## 4. 节点导入设计

### 4.1 数据契约

解析响应的 proxies、errors，以及导入响应的 created、errors 始终为数组，空集合返回 []。前端在响应边界兼容旧后端的 null，不把类型声明当作运行时保障。

保留现有逐条导入语义：部分成功时同时展示成功数量和失败条目，不因一条失败回滚已导入记录。错误条目显示序号与脱敏原因，不输出原始节点密码或完整链接。

### 4.2 交互行为

提交期间禁用重复点击；收到成功响应后先刷新节点列表，再显示结果、清理或保留输入。部分失败保留查看错误的入口，不能清空结果后让用户重复导入整份内容。

响应丢失或网络中断时提示“结果暂不确定，请先刷新列表”，不自动重发创建请求。本轮不引入长期保存节点原始内容的导入任务系统；跨请求去重或幂等任务另行评估。

### 4.3 验收

覆盖全部成功、部分失败、全部失败、空输入、格式无效、旧响应 null、请求失败、重复点击。确认提示数量与数据库新增数量一致，预览不产生节点，导入后无需手动刷新即可见新记录。

## 5. 注册与批量安装设计

### 5.1 令牌与错误

继续采用每台服务器独立、15 分钟有效、仅使用一次的注册令牌。重新生成仅替换对应服务器的令牌，不影响其他服务器。状态查询不返回令牌明文，页面不将命令持久化到浏览器存储或日志。

客户端解析后端允许的错误码，区分令牌过期、无效或已使用，以及长期 agent 身份被撤销。对于非应用返回的 401 显示“入口返回未授权，请检查代理认证”，不暴露第三方原始响应。

界面展示到期时间；重新生成前说明旧命令将失效。发生注册请求已成功但响应丢失时，指导管理员针对该服务器重新生成命令并恢复注册，不能把一次性令牌改成可无限重用。

### 5.2 批量流程

批量入口接收多个服务器名称，创建独立记录，并为每个记录生成各自命令。采用有上限的批次规模和请求并发，每行独立展示成功、失败、有效期及复制按钮。后端按服务器绑定令牌，不产生跨服务器共享令牌。

部分创建或命令生成失败时，只重试失败行；已成功行保留，避免重复创建服务器。离开页面后可以按服务器重新生成命令，不持久化批量明文 token 文件。

本轮可先复用单台创建和令牌接口；若需要新增批量接口，返回逐条结果并保持同样的权限、限流、审计与幂等约束。

### 5.3 验收

并发注册至少三台不同服务器全部成功；同一令牌并发提交仅一次成功；重新生成 A 不影响 B；过期、已使用、复制错服务器命令和响应丢失有明确处理路径。更新已注册 agent 不依赖重新生成注册令牌。

## 6. 在线状态与故障信息

### 6.1 视觉调整

保留现有徽章组件，增强在线底色和边框，添加小圆点并保留“在线”文字。离线与待安装状态采用不同文字和样式，不能仅靠颜色区分。明暗主题正常文字对比度以 4.5:1 为验收目标。

列表中区分“在线但升级失败”“离线”“待安装”，详情中补充最后心跳时间、当前版本、目标版本和最近配置应用结果。自动刷新不得造成布局明显跳动。

### 6.2 验收

用浏览器检查明暗主题、窄屏、长服务器名称、无心跳与维护失败状态。主观“醒目”与实际对比度分别验证；此次改动不延伸为全站样式重构。

## 7. 分享授权与连接日志后续方向

### 7.1 先审计现有能力

已有分享包含配额、到期、状态和连接日志开关。先列出现有入口及行为，再决定是否补充单个分享的停用、恢复和凭据轮换；不重复建设第二套授权系统。

要明确区分停止订阅下载与撤销已下载的代理凭据。暂停、撤销、到期和超额必须验证实际节点侧的凭据或配置收敛；无法实时阻断已有连接时，界面说明具体生效条件。

### 7.2 日志控制

连接日志保持显式开启。先核对当前按节点、按分享和全局的生效关系，再补足缺失的单节点入口；任何层级禁止采集时，下级开关不能绕过。流量计量与访问目标日志分开说明，关闭后者不影响配额计量。

页面说明采集字段、可见角色、保留期限，以及关闭后停止新增但是否仍保留历史数据。提供独立清理动作，明确作用范围；不为诊断临时静默开启采集。

### 8.2 升级矩阵

至少覆盖脚本与 Docker 控制端、Linux amd64 与 arm64 agent、同版本重装与旧版本升级、缺失元数据和 dev 构建、无网络与发行校验失败、目标切换、失败回滚和控制端短暂离线。原生架构运行测试与交叉编译检查分别记录，不能以编译通过替代运行验收。

关键组合：旧控制端加新 agent、新控制端加旧 agent、新控制端加新 agent；自定义 TUF 策略另设用例，不能只测默认官方 HTTPS 摘要校验。

### 8.3 检查与退出条件

1. API 单元与集成测试覆盖契约和授权；前端测试覆盖成功回调与错误恢复。
2. 按项目要求完成 Go vet/test、前端测试/typecheck/build 和 Linux 双架构构建。
3. 安装、升级、恢复在隔离容器执行，包括 scripts/test-maintenance-container.sh。
4. 浏览器完成“添加 → 安装 → 在线 → 部署节点 → 下载配置 → 分享 → 停用或撤销”的验收；涉及真实节点变更另行限定测试对象。
5. 任何校验绕过、错误架构替换、数据丢失、身份串用或不可恢复的升级失败均阻断发布。

## 9. 发布与回滚

### 9.1 单台试运行

在独立候选构建上固定源码版本和制品摘要，完成隔离验收后，再在用户指定目标进行试运行。此前 hostdzire 的部署授权不自动扩展为其他 VPS 的连接或更新授权。

切换前保留旧程序、配置、加密数据备份和目标元数据；记录已安装 agent 的版本与能力。先只升级控制端，再选择一台测试 agent 验证，观察维护完成及至少两轮正常心跳、配置收敛和测试节点可用性，随后才开放后续批次。

### 9.2 回滚条件与方法

服务无法启动、核心接口失败、旧 agent 无法接入或试运行配置无法恢复时停止扩大部署。程序升级失败优先使用已验证的旧程序恢复；如引入数据库字段或任务格式，采用向后兼容迁移，并在变更前验证旧程序读取能力。

恢复整库是单独的最后手段，会丢失备份后的写入，不能静默覆盖正在使用的数据。agent 的回滚由本机维护执行器使用已验证恢复点完成，不由网页传任意程序路径。

### 9.3 对用户的交付说明

最终说明包含安装方式、当前与目标 agent 版本、已验证矩阵、旧端迁移步骤、已知限制和回滚方法。正式 commit、push、Release 发布及新的线上部署按用户后续明确指令执行。

# 1. 线路编排功能设计

状态：当前源码支持两台接入（入口直接转发到落地节点）及三台接入（额外中转）。新线路由用户选择是否添加中转；旧线路保留原拓扑。使用步骤和当前边界以[网络指南第 8 节](network.md#8-配置两台或三台转发线路)为准。本文保留完整功能设计；线路改配和独立接入节点实体尚属后续范围。当前用订阅的 `route_ids` 引用线路，输出时投影原落地节点的已应用参数，不复制节点或凭据。

## 1.1 要解决的问题

当前用户必须分别理解并配置节点、托管中转、固定转发和订阅访问地址。系统管理的是各个资源，用户想管理的却是“从哪个入口连接、经过哪些机器、从哪里出网”这一条完整线路。

优化目标是让用户选择机器角色和已有落地节点，系统生成明确的资源计划、逐段预检、协调应用，并输出正确的客户端接入配置。不能仅给现有按钮换名称，也不能把几个提交请求在浏览器里依次执行就称为线路编排。

## 1.2 两种能力必须分开

| 能力 | 连接由谁解密 | 用途 | 现有底座 |
|---|---|---|---|
| 接入转发 | 最终落地节点 | 改变客户端到节点的接入路径 | 固定端口转发 |
| 节点出口中转 | 入口节点先解密业务，再通过另一段隧道出网 | 改变节点业务的出口 | 托管 WireGuard / SS-2022 中转 |

两者都可以有多台机器，但不是同一种资源关系。第一期分别提供固定模板，不开放任意多跳或两种模板自由嵌套。

控制端负责管理，不算线路中的一跳，业务流量也不需要经过控制端。

# 2. 三机接入线路

## 2.1 推荐拓扑

```text
客户端 → A：国内入口端口 → B：IX 转发端口 → C：落地代理节点 → 网站
```

A、B 只承担固定目标转发，不部署供客户端认证的代理节点。C 上部署实际代理节点。客户端连接 A 的接入地址和端口，使用 C 的节点协议和认证参数。

这是基于现有固定转发能力的编排方案，不负责提供专线本身。A 到 B 的专线接口、路由、地址、商家端口映射和云安全组须由用户或线路供应方准备。

它与“在 B 部署 SS-2022，再托管中转到 C”的组合不同；后者仍作为已有高级能力保留，不作为三机接入的默认模板。

## 2.2 用户需要指定什么

1. 选择国内入口 A。
2. 选择 IX 转发机 B。
3. 选择 C 上已部署的落地节点；尚无节点时先部署。
4. 确认 A 对客户端公布的地址与端口。
5. 确认 A 连接 B、B 连接 C 分别使用的地址、目标端口及本机出站路径。
6. 确认连接类型、来源限制、连接预算和影响预览，提交线路。

相邻机器的目标应按资源身份选择，系统解析出候选地址和端口供确认。不能直接使用节点的订阅地址作为转发目标：该地址可能已指向其他接入入口，造成循环。

监听端口、上游可达端口和订阅公布端口分别建模；NAT 服务器必须使用已确认的映射。A、B、C 的端口不要求相同。

## 2.3 系统生成什么

| 资源 | 所属机器 | 内容 |
|---|---|---|
| 落地节点引用 | C | 引用原节点，不复制密码或创建另一份代理实例 |
| 后段固定转发 | B | B 的监听端口 → C 的节点可达地址与端口 |
| 前段固定转发 | A | A 的监听端口 → B 的可达地址与端口 |
| 线路接入记录 | 控制端 | A 的公布地址与端口、C 的节点引用及线路身份 |

每段复用固定转发的预检、版本、资源隔离、计量与清理回执。线路拥有创建的转发资源，但不拥有被引用的原落地节点，删除线路不能删除 C 的节点。

第一期不接管已有手工转发，避免把其他用途的端口误当成线路资源；后续若支持导入，必须明确依赖关系和所有权。

# 3. 两机出口中转

## 3.1 保留现有语义

```text
客户端 → A：代理节点 → B：隧道落地 → 网站
```

继续复用托管中转的落地先应用、入口后开放、顺序退役和独立计量机制。入口支持受管 sing-box 的 VLESS Reality、Trojan、AnyTLS、Hysteria2、TUIC 与 SS；非原有 SS-2022 AES-128 组合需新 agent 明确上报能力。三机转发的落地已支持受管、导入和手动节点；端点变化、订阅更新和验证边界见 [网络操作](network.md#81-外部落地的端点和订阅变化)。

这一模板中，客户端认证的是 A 的节点；三机接入模板中，客户端认证的是 C 的节点。线路定义必须保存模板类型，禁止靠机器数量猜测工作方式。

## 3.2 当前限制需要直接处理

现有活跃托管中转会禁止普通节点网络改写，不能把“先建中转，再改节点访问地址”当成通用步骤。三机接入模板通过独立线路接入记录解决订阅问题，不放宽托管资源的编辑保护。

# 4. 订阅与分享

## 4.1 线路接入记录

三机线路需要独立的接入身份，内容是线路名称、公布地址和端口、落地节点引用以及启用状态。它不是一个新代理进程，也不是现有客户端链式代理 `NodeChain`。

生成订阅时先验证落地节点和分享的当前有效性，再读取节点当前已应用的参数，最后投影线路的接入地址与端口。撤销、暂停、过期、耗尽和认证轮换必须沿用源节点的权限与应用回执，不能使用旧参数快照恢复访问。

不能直接改 C 的节点地址为 A：同一个落地节点可能还用于直连或另一条入口线路。每条线路的公布地址应独立存在。

## 4.2 协议参数

替换接入地址不能同时改变 TLS 的 SNI、证书校验域名、Reality 参数或其他握手参数。源节点依赖默认主机名推导 SNI 时，必须先固定其原有效值，再替换连接地址；不能因此关闭证书校验。

第一期仅开放已通过真实转发和客户端格式验证的组合。TCP、UDP、端口跳跃、来源地址依赖等能力逐项检查，不能因为固定转发支持某种传输，就宣称所有代理协议均可用。

## 4.3 计费

A、B 的固定转发各自记账，C 的节点与分享保留原有记账。它们是不同采集对象，不相加成为一份分享用量，不重复扣分享配额。各服务器仍使用自身的网卡和配额设置。

多个入口共享同一落地节点时，共用源节点及分享权限；第一期不宣称能区分每条入口贡献的落地分享用量。

# 5. 后端编排与故障恢复

## 5.1 资源模型

增加线路及版本、分段资源引用和持久化操作记录。线路类型第一期固定为“单段接入转发”“三机接入转发”“两机出口中转”。原有固定转发和托管中转继续作为执行资源，不再造一套 agent 转发协议。

线路提交以 operation ID 幂等，固定预期配置版本和完整影响预览摘要。预览后任一机器、端口、节点参数或依赖发生变化，都必须重新核对。线路保存、端口预留及编排意图应在控制端事务中持久化，网络发布在事务后执行。

禁止浏览器充当调度器；关闭页面、控制端重启或重复点击不应丢失进度或重复分配端口。

## 5.2 创建顺序

1. 核对三台机器身份不同、源节点有效、端口无冲突、传输和 NAT 能力匹配。
2. 持久化线路意图及分段资源，外部入口保持未开放。
3. 核对 C 当前匹配的应用回执，再配置 B → C。
4. B 的匹配版本应用成功后，再配置 A → B。
5. A 应用成功且依赖仍有效后，允许订阅输出线路接入记录。
6. 实际连接测试独立记录；没有端到端证据时，只能标记“配置已应用，连通性待验证”。

状态至少区分：等待预检、等待落地、等待后段、等待前段、配置已应用、应用失败、正在停止、正在清理、已退役。机器离线单独展示，不能等同应用失败，也不能拿旧回执显示最新版本成功。

## 5.3 修改、停止和删除

修改先撤下旧线路的订阅接入资格并提交入口阻断，确认后更新后段，最后恢复入口；第一期接受明确提示的连接中断，不承诺无损切换。C 的源节点配置不因线路修改而被覆写。

停止或删除先撤下线路接入记录，再阻断 A，确认后清理 B，最后结算并释放各自端口。任一端离线，保持待清理状态并继续预留资源，不能只删除控制端记录。引用原节点仍可用于其他线路。

失败重试从持久化阶段恢复，只操作该线路拥有的资源。不得改为直连、放宽私网授权、自动更换内核版本或把失败段跳过。

已有固定转发的健康租约只保护其特定故障场景，不提供整条线路的端到端健康或通用远端断路。第一期只能报告观测到的故障并协调阻断，不承诺瞬时联动关闭所有机器；出口切换与自动故障切换另行设计。

# 6. 预检边界

1. 逐段核对 agent 能力、官方内核兼容版本、来源 ACL、连接预算、监听地址及公网端口映射。
2. 公网与私网地址分别验证。私网固定目标沿用按资源 ID 精确匹配的本机授权；需要先分配资源身份时，只能保存阻断状态，等待本机授权后继续。
3. 当前私网 UDP 固定目标尚未开放，三机模板遇到该组合必须拒绝启用，不能把它包装成已支持的专线方案。
4. 来源 ACL 依据下游实际看到的上游出站地址配置；经过 NAT 时不能直接使用服务器登记地址猜测。最终代理协议凭据仍由 C 校验。
5. 固定转发不会保留客户端源地址到 C。依赖原始源地址的计费、访问限制或协议需要单独验证。
6. 仅指定网卡或源地址不保证改变宿主机路由；线路供应方的真实路径不能由面板选项推定。TCP 半关闭与 UDP 零负载报文限制继续生效。

# 7. 实施顺序与验收

## 7.1 第一阶段：最小可用线路

实现公网 TCP 的单段和三机固定接入模板、持久化编排、独立订阅接入记录及顺序退役。复用现有原语，但补齐线路所有权、跨段依赖和源节点有效性检查。

先验收一个明确的 TCP 代理协议与客户端组合，再按矩阵扩大范围。不把第一阶段包装成通用专线管理。

## 7.2 第二阶段：明确扩展

分别增加私网 TCP 精确授权流程、已支持条件下的公网 UDP，以及其他经验证的节点和客户端组合。私网 UDP、任意多跳、链路自动切换和带宽叠加不混入本次范围。

## 7.3 必须通过的验证

1. 三台隔离 agent 环境完成真实客户端连接，确认客户端连接 A、认证发生在 C、目标侧看到 C 的出口。
2. A、B 和 C 使用不同端口，含 NAT 映射；订阅地址与转发目标不会串用或产生循环。
3. 重复提交、重启、任一端离线和应用失败均可恢复，且不重复占端口。
4. 修改和删除时，入口先阻断、离线端保留清理意图、最终计量不丢失、其他线路和原节点继续保留。
5. 源节点撤销、分享过期或配额耗尽后，所有相关接入记录均不可继续输出；旧成功回执和缓存不能复活它们。
6. 同一落地节点同时用于直连及两条线路，地址互不覆盖；密码轮换只输出已确认应用的参数。
7. TLS/Reality 等组合保持原握手校验参数；不支持的私网 UDP 和依赖原始源地址的组合明确被阻止。

# 8. 代码落点

| 范围 | 实施位置 |
|---|---|
| 线路、版本、资源所有权与幂等操作 | `internal/domain`、`internal/store`，复用现有网络操作和 outbox 机制 |
| 预览、创建、修改、重试、退役 API | `internal/api`，沿用网络影响校验及现有管理员权限 |
| 固定目标转发及本机隔离 | 复用 `internal/networkconfig`、`internal/core`、agent 的既有固定转发能力 |
| 接入记录、权限过滤和格式输出 | `internal/subscription`，先核对源节点当前授权与已应用参数，再投影接入地址 |
| 回归与真实链路验证 | store/API 状态机测试，以及现有隔离容器验证框架 |
